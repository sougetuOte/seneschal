# core/ — 委任範囲

**主人にしか決められないのは3つ。ゴール合意（G0）／不可逆操作（G1）／統治の自己改変（G2）。残りは Seneschal が決めて進める。**
**骨格（条文3本と、プラグインの skill と agent の定義）の Markdown は上限15本。現在 9本。**

**これは単独で完全になる物ではない。**プロジェクトを回す間の補助であり、ベンダー（Claude Code）と
モデルが伸びれば要らなくなる。**足す物・取り入れる物には、すべて消滅条件を書く** ── 条文だけでなく、
証拠（`docs/research/`）も、外から採ってきた規律も。何が起きたら消せるかを書き、起きたら消す。
書けないなら足さない。**「なし（当面は消さない）」も消滅条件である** ── そう書いた物は将来見直せばよい。
**対にもう1つ。削って残した物には、戻す条件を書く** ── 書けないなら、削ったのではなく忘れただけである
（ponytail の `ponytail:` コメントから採った。**消滅条件：この対の1行が2回続けて空振りしたら外す**）。
証拠は放っておくと利子が付く（N 本貯めると整合の手間が N に比例し、整合の記録がまた1本増える）。

## 3ゲート

| ゲート | 発火点 | 機構 | 機構の所在 |
|---|---|---|---|
| **G0** ゴール合意 | 新規フェーズ／Wave の開始前。`goal.md` に「完了条件・検証方法・やらないこと」を書いて主人が承認 | `loop.md` の面接手順（プロンプト） | 本リポジトリ |
| **G1** 不可逆操作 | 外部コード/MCP 導入、本番投入、削除、リポジトリ外書込、外部送信 | ベンダー（auto mode の classifier、Containment Escape、`blockReadsOutsideWorkingDirectories`、主人環境の `permissions.deny` と `pretooluse-safety.sh`） | **本リポジトリの外。確率的。Claude Code 限定** |
| **G2** 統治自己改変 | `CLAUDE.md`・`core/`・`adapters/`・`rubrics/`・`goal.md`・deny リスト自身への書込 | `.claude/settings.json` の `permissions.deny` ＋ `.githooks/pre-commit` | 本リポジトリ**の中だけ**。**判定は決定的、執行は自己拘束**（下記）。**dogfood 先では機構なし**（下記） |

**G1 の機構はここに無い。**使う側はこれを知った上で使う。

**G2 の第1層（deny）の境界は確率的である。**ベンダーの解析器が「パスとして認識した」書込だけが止まる。
同じヒアドキュメント形が、あるコンテキストでは通り、別のコンテキストでは拒否された（2026-09-10 実測。
`docs/research/2026-09-10-g2-deny-boundary.md`）。**穴を列挙して塞ぐ設計は原理的に成立しない。**
そこで**書込ではなく「commit に載ること」を止める**（下記）。

**G1 と G2 を統合しない。**「取り消せない書き込み」で括りたくなるが、`CLAUDE.md` の書き換えは git で戻せる。
G2 の本質は可逆性ではなく**規範の対象者が規範を書くこと**である。機構の性質も違う（外／確率的 と 内／決定的）。

## G2 の第2層 — `.githooks/pre-commit`

git は staged なパス一覧を自分で持っているため、**判定に推測が要らない**。ここだけが決定的にできる層である。
`CLAUDE.md` / `goal.md` / `core/` / `adapters/` / `rubrics/` / `.claude/settings.json` / `.githooks/` を含むコミットを拒否する。
`adapters/` は 2026-09-26 に足した（主人決定）── 配り先に注入される評価器と読み手の契約は、規範の側である。
**第1層と保護範囲が違う** ── `.githooks/` は deny に無く、作業ツリーでのフック書き換えは止まらない（主人が
`settings.json` に足せば揃う）。`.claude/settings.local.json` は**第1層には入った**（主人が deny に2行追加）が、
**第2層の `PROTECTED` には無い**。

**フックは `trap '' PIPE` で始める。**stderr に書いてから `exit 1` する構造のため、`git commit … | head` で
パイプの読み口が先に閉じると、フックは `exit 1` に到達する前に SIGPIPE で死に、native の git.exe は
シグナル死の下位8ビット（0）しか見ずに**コミットを作る**。
素のフックで**すり抜け 10/10**、修正後**阻止 10/10**（2026-09-11 実測）。

```
git config core.hooksPath .githooks   # clone 後に1回
SENESCHAL_G2=approved git commit ...  # 承認するとき（sh / bash）
```
```
$env:SENESCHAL_G2="approved"; git commit ...; $env:SENESCHAL_G2=$null   # PowerShell
```
PowerShell には `VAR=value cmd` の形が無い。**消す所までが1行**（`$env:` はシェルに残り、
残せばそれが常設の自己承認になる）。主人の既定シェルはこちら。

**`SENESCHAL_G2` の範囲。**主人は 2026-09-10 に承認変数を Seneschal に委ねたが（骨格建設中の `core/` の新規作成まで）、
**2026-09-26 に外した** ── 骨格の建設は終わった（「骨格はこれ以上足さない」）。**いま Seneschal が自分で付けてよい場面は無い。**
統治文書の変更は、主人が承認し、主人の手で置き、主人が変数を付けて commit する。無制限の常設許可として扱えば G2 は空になる。
**機構はこの区別を持たない**（変数は自己承認と主人承認を区別しない）。区別は本節が持つ。
**戻す条件：新しい骨格を建てると主人が決めたら、その範囲に限って委ね直す。**

**買えるのは「事故の防止」であって「意図の防止」ではない。**
`--no-verify`、`core.hooksPath` の解除、フックそのものの書き換え、承認変数の自己付与で越えられる。
リポジトリの中にある機構は、中にいる者に対して不可侵にはできない。
**測って見つかった穴は塞がない**（D16）。`git -c core.hooksPath=/dev/null commit`、`cherry-pick`・`rebase`・
`merge`・`am`・`reset --hard`（いずれも pre-commit を起動しない）など、経路は列挙し切れない。
穴の数だけ機構を足せば、ハーネスが製品になる。**直すのは判定式のバグだけ** ── 非ASCII 名と rename の
2つは「`core/` を含むコミットを拒否する」という宣言を実装できていなかったので、判定式を直した（機構は増えない）。
このゲートが変えるのは、統治文書の変更が**黙って起きるか、diff とコマンド列に残る明示的な行為になるか**である。
不可侵にしたければ層が1つ上に要る ── `.claude/settings.json` の `ask` に `Bash(git commit:*)` を置き、
ベンダーに主人へ問わせる。**それは主人にしか置けない**（本リポジトリの deny がその変更を拒む）。

## dogfood 先の G2 には機構が無い

**`goal.md` の保護は、`goal.md` を使う場所には無い。**本リポジトリでは `goal.md` は deny で守られているが、
ここでは `goal.md` を使わない（`loop.md` の面接節。3項は `docs/research/` に置く）。
実際に使う dogfood 先には deny も pre-commit も無く、**承認後の `goal.md` を Seneschal が書き換えられる**
（2026-09-12 実測。ある配り先の `.claude/settings.json` に `permissions` キーが無く、相手の pre-commit に `goal` は0件）。
G1 と同じく、**使う側はこれを知った上で使う。**

**相手リポジトリで何が G2 かは、`goal.md` の「やらないこと」に書く。**相手の統治文書の所在は相手ごとに違い
（ある配り先では `ops/methodology/` `.claude/rules/` `.claude/settings*.json` の3つ）、こちらの条文では列挙できない。
**書き忘れたら、その回は守られていない。**相手の機構に載せてもらうのは D13（完全切断）と衝突するので採らない。

## ゲートの外は止めない

3ゲートに当たらない操作は、Seneschal が判断して進める。確認を取りに戻らない。
迷ったら止めるのではなく、`goal.md` の「やらないこと」に当たるかを見る。当たらなければ進む。

**例外は1つ。`goal.md` のとおりには満たせないと分かったら、回り道で満たさない。**欠けている物を添えて主人へ戻る ──
G0 のやり直しであって、FAIL を待たない。確認を禁じたまま満たせない課題を渡すと、モデルは回り道を選びやすい
（Claude Opus 5.5 System Card §6.2.2：確認を求めるなと指示された、満たせない課題で、報酬ハッキングの試みが3〜6倍）。
deny や判定器に止められた操作は G1 に当たった物なので、別の経路で取りにいかず主人へ渡すキューに載せる。
**機構: なし。消滅条件：ベンダーの評価が、満たせない課題での回り道を満たせる課題と同程度と報告したら。**
