# core/ — 委任範囲

**主人（Seneschal に仕事を任せる人）にしか決められないのは3つ。ゴールの合意（G0）／取り消せない操作（G1）／統治文書の書き換え（G2）。残りは Seneschal が決めて進める。**
**Seneschal 自身の骨格（条文3本と、プラグインの skill と agent の定義）の Markdown は上限15本。現在 9本。**

**これは単独で完全になる物ではない。**プロジェクトを回す間の補助であり、ベンダー（Claude Code）と
モデルが伸びれば要らなくなる。**足す物・取り入れる物には、すべて消滅条件（何が起きたら消すか）を書く** ── 条文だけでなく、
調べた証拠の文書も、外から採ってきた規律も。何が起きたら消せるかを書き、起きたら消す。
書けないなら足さない。**「なし（当面は消さない）」も消滅条件である** ── そう書いた物は将来見直せばよい。
**対にもう1つ。削って残した物には、戻す条件を書く** ── 書けないなら、削ったのではなく忘れただけである
（**消滅条件：この1行が2回続けて役に立たなかったら外す**）。
証拠は放っておくと利子が付く（N 本貯めると整合の手間が N に比例し、整合の記録がまた1本増える）。

## 3ゲート

| ゲート | 発火点 | 機構（止める仕組み） | 機構の所在 |
|---|---|---|---|
| **G0** ゴールの合意 | 新しいフェーズや Wave（いくつかのフェーズのまとまり）を始める前。`goal.md` に「完了条件・検証方法・やらないこと」を書いて主人が承認する | `loop.md` の面接の手順（プロンプト） | Seneschal の条文 |
| **G1** 取り消せない操作 | 外部のコードや MCP の導入、本番への投入、削除、リポジトリの外への書き込み、外部への送信 | ベンダー（auto mode の classifier など）と、主人が置いた `permissions.deny` や PreToolUse の hook | **Seneschal の外。確率的。Claude Code 限定** |
| **G2** 統治文書の書き換え | そのプロジェクトの規範を書いた文書（`CLAUDE.md`・`goal.md`・deny の一覧そのものなど）への書き込み。何が当たるかは `goal.md` の「やらないこと」に書く | **Seneschal には入っていない。**機械で止めたければ、使うプロジェクトに deny と pre-commit の hook を置く（下の「例」） | 使うプロジェクトの中だけ。pre-commit を置いた場合、**判定は決定的、執行は自己拘束**。deny だけでは確率的（下の「例」） |

**G1 の機構は Seneschal の中に無い。**使う側はこれを知った上で使う。

**G1 と G2 を統合しない。**「取り消せない書き込み」で括りたくなるが、`CLAUDE.md` の書き換えは git で戻せる。
G2 の本質は可逆性ではなく**規範の対象者が規範を書くこと**である。機構の性質も違う（G1 は外にあって確率的、G2 は pre-commit を置けば中にあって決定的）。

## 使うプロジェクトの G2

**Seneschal を入れただけでは、G2 を止める物は何も無い。**承認後の `goal.md` も Seneschal が書き換えられる
（2026-09-12 実測。使う側のプロジェクトの1つでは、`.claude/settings.json` に `permissions` キーが無く、pre-commit も `goal.md` を見ていなかった）。
G1 と同じく、**使う側はこれを知った上で使う。**

**何が G2 かは、`goal.md` の「やらないこと」に書く。**統治文書の所在はプロジェクトごとに違い
（あるプロジェクトでは `ops/methodology/` `.claude/rules/` `.claude/settings*.json` の3つだった）、条文では列挙できない。
**書き忘れたら、その回は守られていない。**機械で止めたければ、下の「例」の形を使うプロジェクトに置ける。
そのとき `goal.md` は deny に入れず、pre-commit だけで守るのがよい。deny に入れると Seneschal は `goal.md` を書けなくなり、3項を別の文書に置くことになる（`loop.md` の面接の節）。
面接で書いた `goal.md` も pre-commit の一覧に当たるので、最初の commit は主人が承認のときに変数を付けて打つ。Seneschal は `goal.md` を stage しない（変更を巻き込むので `git commit -a` も使わない）。

## 例：Seneschal の開発用のリポジトリの G2

Seneschal 自身の開発用のリポジトリ（非公開）は、G2 を2層で止めている。使うプロジェクトで同じことをするときの手本になる。
第2層（pre-commit）が守る文書は `CLAUDE.md`・`goal.md`・`core/`・`adapters/`・`rubrics/`・`.claude/settings.json`・`.githooks/` である。
`core/` は条文、`adapters/` はプラグインの定義（使う側に入る評価器と読み手の契約も、規範の側に入れた）、`rubrics/` は採点表の置き場として一覧にだけ入れてあり、中身はまだ無い。

**第1層は `.claude/settings.json` の `permissions.deny` で、境界は確率的である。**ベンダーの解析器が「パスとして認識した」書込だけが止まる。
同じヒアドキュメントの形が、あるコンテキストでは通り、別のコンテキストでは拒否された（2026-09-10 実測）。**穴を列挙して塞ぐ設計は原理的に成立しない。**
そこで**書込ではなく「commit に載ること」を止める**のが第2層である。

**第2層は `.githooks/pre-commit` である。**git は stage されたパスの一覧を自分で持っているため、**判定に推測が要らない**。ここだけが決定的にできる層である。
上の一覧を含む commit を拒否する。**第1層と守る範囲が違う** ── `.githooks/` は deny に無く、作業ツリーでのフックの書き換えは止まらない（deny に足せば揃う）。
`.claude/settings.local.json` は第1層には入れたが、第2層の一覧には無い。deny のフォルダの規則は下の階層の同じ名前のフォルダにも効くが、フックの一覧は先頭からのパスだけを見る。

第1層の deny は、次の形で書く（抜粋）。パスは使うプロジェクトの統治文書に替える。`Edit(パス)` の規則は、Write を含む書き込みの道具すべてに効く。`./core/**` のようなフォルダの規則は、下の階層にある同じ名前のフォルダ（たとえば `src/core/`）にも効く（ベンダーの文書。2026-10-14 にも観測した）。統治文書でない同じ名前のフォルダがあるプロジェクトでは、Seneschal がそこを書けなくなるので、守るフォルダの名前を替える。開発用のリポジトリは `goal.md` も deny に入れているので、Seneschal は `goal.md` を書けず、3項を `docs/research/` に置いている。

```json
{
  "permissions": {
    "deny": [
      "Edit(./CLAUDE.md)",
      "Edit(./.claude/settings.json)",
      "Edit(./core/**)",
      "Edit(./adapters/**)"
    ]
  }
}
```

第2層のフックの要は次の行である（開発用の `.githooks/pre-commit` から、メッセージを短くした）。`PROTECTED` と変数の名前は、使うプロジェクトの統治文書と好きな名前に替える。
`-z` と `--no-renames` は外さない。`-z` が無いと、git は非ASCII を含むパスを引用符で囲んで出し、前方一致が外れる。`--no-renames` が無いと、rename で新しいパスしか出さず、`git mv core/X docs/X` が通る。

```sh
#!/bin/sh
trap '' PIPE
PROTECTED='^(CLAUDE\.md|goal\.md|\.claude/settings\.json)$|^(core/|adapters/|rubrics/|\.githooks/)'
HITS=$(git diff --cached --name-only -z --no-renames | tr '\0' '\n' | grep -E "$PROTECTED")
[ -z "$HITS" ] && exit 0
[ "$SENESCHAL_G2" = "approved" ] && exit 0
echo "G2: 統治文書の変更には主人の承認が要る。承認するときは SENESCHAL_G2=approved を付けて commit する" >&2
echo "$HITS" >&2
exit 1
```

**フックは `trap '' PIPE` で始める。**stderr に書いてから `exit 1` する構造のため、`git commit … | head` で
パイプの読み口が先に閉じると、フックは `exit 1` に到達する前に SIGPIPE で死に、Windows の git.exe（native 版）は
シグナル死の下位8ビット（0）しか見ずに**コミットを作る**。
素のフックで**すり抜け 10/10**、修正後**阻止 10/10**（2026-09-11 実測）。

```
git config core.hooksPath .githooks   # clone 後に1回
chmod +x .githooks/pre-commit          # Windows 以外では要る。実行権限が無いと git は黙って無視する
SENESCHAL_G2=approved git commit ...  # 主人が承認するとき（sh / bash）。フック自身を入れる最初の commit にも要る
```
```
$env:SENESCHAL_G2="approved"; git commit ...; $env:SENESCHAL_G2=$null   # PowerShell
```
PowerShell には `VAR=value cmd` の形が無い。**消す所までが1行**（`$env:` はシェルに残り、
残せばそれが常設の自己承認になる）。

**承認変数を Seneschal が自分で付けてよい場面は無い。**統治文書の変更は、主人が承認し、主人の手で置き、主人が変数を付けて commit する。
無制限の常設許可として扱えば G2 は空になる。**機構はこの区別を持たない**（変数は自己承認と主人の承認を区別しない）。区別は本節が持つ。
**戻す条件：主人が範囲を決めて委ねたら（たとえば新しい統治文書を書き起こす間）、その範囲に限って付けてよい。**
開発用のリポジトリでは、骨格（条文とプラグインの定義）を建てる間だけ委ねられ、建て終えた 2026-09-26 に外された。

**買えるのは「事故の防止」であって「意図の防止」ではない。**
`--no-verify`、`core.hooksPath` の解除、フックそのものの書き換え、承認変数の自己付与で越えられる。
リポジトリの中にある機構は、中にいる者に対して不可侵にはできない。
**測って見つかった穴は塞がない。**`git -c core.hooksPath=/dev/null commit`、`cherry-pick`・`rebase`・
`merge`・`am`・`reset --hard`（いずれも pre-commit を起動しない）など、経路は列挙し切れない。
穴の数だけ機構を足せば、ハーネスが製品になる。**直すのは判定式のバグだけ** ── 非ASCII 名と rename の
2つは「`core/` を含むコミットを拒否する」という宣言を実装できていなかったので、判定式を直した（機構は増えない）。
このゲートが変えるのは、統治文書の変更が**黙って起きるか、diff とコマンド列に残る明示的な行為になるか**である。
普段の形の commit を主人の目に通したければ、`.claude/settings.json` の `ask` に `Bash(git commit:*)` を置き、
ベンダーに主人へ問わせる。ただし `git -C` や `git -c` を付けた形には当たらない（ベンダーの文書）ので、これも不可侵ではない。
**この設定は主人にしか置けない**（開発用のリポジトリでは、deny がその変更を拒む）。

## ゲートの外は止めない

3ゲートに当たらない操作は、Seneschal が判断して進める。確認を取りに戻らない。
迷ったら止めるのではなく、`goal.md` の「やらないこと」に当たるかを見る。当たらなければ進む。

**例外は1つ。`goal.md` のとおりには満たせないと分かったら、回り道で満たさない。**欠けている物を添えて主人へ戻る ──
G0 のやり直しであって、FAIL を待たない。確認を禁じたまま満たせない課題を渡すと、モデルは回り道を選びやすい
（Claude Opus 5.5 System Card §6.2.2：確認を求めるなと指示された、満たせない課題で、報酬ハッキングの試みが3〜6倍）。
deny や判定器に止められた操作は G1 に当たった物なので、別の経路で取りにいかず主人へ渡すキューに載せる。
**機構: なし。消滅条件：ベンダーの評価が、満たせない課題での回り道を満たせる課題と同程度と報告したら。**

## core/ の中身

| ファイル | 中身 |
|---|---|
| `README.md` | 本ファイル。委任範囲の正本 |
| `loop.md` | 回し方。面接→フェーズ分割→委譲→検収→キュー |
| `handoff.md` | 引き継ぎの様式。SESSION_STATE / tasks.md / goal.md |

### 作らないファイル（保守する側の覚え）

**`gates.md` は作らない。**本ファイルが3ゲートの正本であり、G0 の手順は `loop.md` にある。分かれた物を1本にまとめ直す層は要らない。

**`evaluator.md` も作らない。**評価器 columba の契約は
プラグインの `agents/columba.md` 1本に入る ── **隔離2項**は `tools:` / `disallowedTools:` が
強制されることで足りる（プラグイン経路でも効くことを agent 一覧で確認した）。
**評価3項に機構は無い。プロンプトで回す。**frontmatter の `hooks:` が subagent の停止で発火するのは
`.claude/agents/` 経路での実測であり、**プラグイン経路では無視される**とドキュメントは言う（未測）。
機械で強制すると決めたら、経路はプラグインの `hooks/hooks.json`（matcher `^seneschal:columba$`）になる。
**戻す条件：Claude Code 以外の道具でも使うことになったら書く**（frontmatter の hooks を持たない道具では、契約を散文で持つ場所が要る）。
