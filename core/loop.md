# loop.md — 回し方

**順番と止め時だけを書く。**委任範囲は `README.md`、引き継ぎの様式は `handoff.md` にある。
**消滅条件**：ベンダーが面接から検収までを回すようになったら消す。

**G0 の面接は自前で持つ。**ワークフロー（Claude Code の Workflow ツールで、スクリプトから subagent を回す仕組み）の中から主人へ問う口は無い（2026-09-11 実測。
`AskUserQuestion` は workflow subagent に存在せず、script の口にも無い）。
ワークフローを起動するときの許可ダイアログも、**auto mode では出ない**（作者の環境で確認。**auto mode 以外では未測**）。
**機構: なし。**ここはプロンプトで回す ── 入口だけの承認でも、面接は起動前に置くことになる。

---

## 1周

```
面接(G0) → フェーズ分割 → 委譲 → 検収 → キュー
```

### 面接（G0）

問うのは3つだけ ── **完了条件 / 検証方法 / やらないこと**。`goal.md` に書いて主人が承認する（様式は `handoff.md`）。
フェーズの種別は5つある。feature（新しい物を作る）、fix（検収の FAIL や不具合を直す）、upkeep（依存やモデルの更新に合わせる）、release（出荷する）、retire（やめる・消す）。
G0 が要るのは feature と retire。fix と upkeep は省略してよい。release は G1 扱い。

**承認を求める前に、完了条件と検証方法の対応を数える。**対応の無い完了条件は採点されない ──
書いた本人が満たしたつもりでいるだけになる（開発中に使う側のプロジェクトで試したとき、3件あった ──
**どれも「こう動く」と書いた条件に、それを確かめる行が付いていなかった**）。
**索引（SESSION_STATE.md）に宿題として書いても、実装するセッションには渡らない。**実装するセッションが読むのは条文と `goal.md` なので、宿題は `goal.md` の検証方法の行にする（次の段落）。

**前のフェーズから持ち越す物を、検証方法の行にする。**前の G0 の起点から今までのコミットのうち採点されなかった物
（採点範囲外の印・PASS の後の直し・締め）と、締めで索引に書いた状態の主張（「〜が一致する」「〜は修正済み」）は、
誰にも採点されていない。主張は**それが指す場所を列挙して**確かめる行にする ── 一部を確かめて全部と書く型は、場所を挙げないと同じ狭さで通る。
**主人の言葉を引く行**は、報告にあることではなく、セッションの記録に主人の発話として在ることを確かめる。
**テストを物差しにする行**は、評価器が自分で走らせるか、走らせられなければ実行器が出した結果ファイルを、成果コミットより後に作られたことと併せて確かめる。
どちらもできなければ、その数は自己申告だと行に書く。起点から今までのテストの削除・skip・期待値の変更を数え、期待値の出所（主人の確定値・仕様）を書く。
**repo の外にある物差しを使う行**（個人情報のため repo に置けない一覧など）には、その絶対パス、中身を出さずに形を確かめる方法（行数、空行、行末の空白）、当たった中身を報告に出さない検索の方法（件数やファイル名だけを出す）を書く。
一覧に漏れが無いことは中身を見ずには測れないので、主人が確かめた発話を引く。書かなければ評価器は物差しを見つけられず、「測れていない」で FAIL を返す（2026-09-29、使う側のプロジェクトの検収で1回あった）。
release は G0 を持たないので、G1 の差し出しに同じ列挙を添える
（開発中の試しで、締めで書いた状態の主張とテストの数の自己申告が、採点されずに次のフェーズへ渡っていた）。
**機構: なし**（G0 の行になれば評価器の採点に載る）。**消滅条件：評価器と同じ**（ベンダーの検収が `goal.md` を接地に採れるようになったら）。

**主人に出す問いは1通にまとめる。**開発中の最初の試しで、主人が手を入れた回数が見積もりの4回から2回に減った理由の半分はこれだった
（残り半分は運。介入回数そのものは指標にしない）。

**`goal.md` を deny で守っているプロジェクトでは、Seneschal は `goal.md` を書けない**（deny の境界は確率的なので、書けてしまったら元に戻して主人に伝える）。
そのときは3項を別の文書に置いて主人に承認を求め、検収では columba にその文書のパスを渡す（Seneschal の開発用のリポジトリでは `docs/research/` に置いている）。
代わりの文書は G2 の機構の外にあるので、承認の後に書き換えられても機械では止まらない（`README.md` が `goal.md` を deny に入れないよう勧めるのはこのためである）。矛盾ではなく、
**規範の対象者が規範を書かない**という G2 の当たり前の帰結である。

### フェーズ分割

1フェーズ ＝ `tasks.md` の1タスク ＝ 1委譲単位。それ以上分けられないなら大きすぎる。

### 委譲

implementer は別セッション。**Workflow ツールを使ってよいが、承認の粒度はワークフロー1本である** ──
起動を通せば以降のフェーズは無承認で走る。だから**主人の承認が要る作業をワークフローの中に入れない。**
主人の承認を得て別のリポジトリのファイルを書き換えるときは（リポジトリの外への書き込みは G1）、**Bash ではなく Write / Edit を使う**（deny や PreToolUse の hook はツール名とパスで判定するので、Bash を通した書き込みは見落とされることがある）。

### 検収

評価器 columba が見る（別コンテキスト・Write/Edit 無し・既定 FAIL。契約はプラグインの `agents/columba.md`）。
**接地（採点の物差し）は毎回 `goal.md` の「検証方法」から採る。**汎用の採点表を先に作らない ──
開発中の最初の試しでは、前もって用意した2つの採点表はどちらも使われず、接地は git の差分形状になった。
**G0 を省略した回（fix / upkeep）は `goal.md` が無く、接地が存在しない。**省略してよいのは採点しなくてよい回だけである ──
**統治文書に触る回は、種別が upkeep でも `goal.md` を書く。**さもないと G2 の変更が、最も危ない種類でありながら
主人の承認だけで入り、誰にも採点されないまま残る（2026-09-20 の開発中の試しで、統治文書の変更2本が検収を通らずに入っていた）。

**採点範囲はフェーズの成果コミットに限る。**主人が別途指示した作業は別コミットに分け、範囲から外す。
**成果コミットは1本とは限らない。**検証方法に「成果コミット1本」と書かない ── 往復が複数セッションに跨れば
成果は複数になり、訂正コミットも付く（開発中の試しで、成果2本と訂正1本になった回があった）。**「本フェーズの成果コミット」と書く。**
範囲にフェーズ外の作業が混ざると、**主人の指示が「やらないこと」の違反として計上される**
（2026-09-12 の開発中の試しで、検証方法9項目は全 PASS だったのに、範囲の取り方で落ちた）。
併せて `goal.md` の「やらないこと」は、**「このフェーズではやらない」と「起きてはならない」を書き分ける。**
columba は条文どおりに読む。読み替えを期待しない。

### キュー

フェーズ末に4つ。**主人へ渡すキュー**（3ゲートに当たる件だけ）／`SESSION_STATE` の更新／`tasks.md` に ☑／
**消滅条件が発火した物を消す。**4つ目を工程にしないと、条文と証拠は「書いた者が覚えている間だけ」しか消えない
（実際に、発火済みの決定と調査文書を残したまま次へ進んだことがある ── 別のモデルによるレビューで見つかった）。
**機構: なし**（フェーズ末に人が見る）。**消滅条件：2回続けて消し忘れたら、機械に見つけさせる形を考える。**
**検収の後に統治文書を触るなら、差分を主人に見せてから commit する。**評価器の観測を直すだけの小さな変更でも同じ ──
フェーズ末の締めは検収を通らない（開発中の試しで、締めのコミットが、主人の最後の発言より後に返った観測を受けて
統治文書を直し、「主人承認」と書いていた）。

## 止め時

**横 ── 予算（ワークフローに渡した上限）を使い切ったら、そのフェーズを置いて次のフェーズへ。**
ワークフロー内の計器は `budget.remaining()` だが、**主人が予算を明示した回しか目盛りを持たない**
（既定は `null`／`Infinity`。2026-09-11 実測）。それ以外の回の**機構: なし。**人が見る。

**縦 ── 同一フェーズで FAIL 2回 → MAGI を1回 → なお FAIL なら主人へ。**
MAGI は、批判役に別のモデルを置いた合議である。MAGI の手順のファイルを **Read で読んで回す**。MAGI そのものは Skill ツールでは呼ばない（主人の呼び出し用に閉じてある）。
手順のファイルの場所は、入口を `条文` の引数で起動すると出る表にある（入口は Skill ツールで起動してよい）。買うのは上のモデルではなく**別のモデルの目**である。
**FAIL の原因が契約（`goal.md`）の側なら、縦に上げずに主人へ戻す** ── 前提の誤りは別のモデルの目でも直せない。G0 のやり直しである。
**検収の結果は回ごとに報告へ1行残す**（何回目か・PASS/FAIL・事由）。**2つ目の FAIL を書いた時点で、縦の停止と retro の1つ目に当たる**
（開発中の試しで、同一フェーズで2回 FAIL し、2回目は契約の誤りで主人へ直行したのに、縦の停止にも retro にも誰も気づかなかった）。
横（フェーズを置く）と縦（段を上げる）を1つの規則にまとめない。**機構: なし。**

3ゲートに当たらない限り主人に戻さない。迷ったら `goal.md` の「やらないこと」を見る。当たらなければ進む。

## retro（振り返り）の起動条件

**カレンダーで起動しない。**次の3つが起きた回にだけ回す。どれも新しい計器を要しない。

1. **縦の停止が発火した** ── 同一フェーズで検収が2回 FAIL した
2. **主人が3ゲート以外で差し戻した** ── 委任範囲の線を越えたか、届かなかった
3. **出荷した物が次の回で直しの対象になった** ── release を通った物が fix の起点になった

**機構: なし**（人が気づく）。**起きた回は `SESSION_STATE` の「これまで」に1行残す** ── 残らなければ、
セッションを跨いだ時点で気づく人がいなくなる（回数を持つ場所は他に無い）。
**消滅条件**：3回回して学びが1件も出なかったら retro をやめる。

## 再開したとき

**`SESSION_STATE` の「次の一手」をそのまま実行しない。**あれは索引であって承認ではない。
compaction や別セッションから戻ったら、そのフェーズに G0 が要るかを先に見る ──
要るなら面接からやり直す。要らない種類（fix / upkeep）はそのまま進む。
**これが無いと、復帰のたびに G0 が黙って迂回される。機構: なし。消滅条件: なし（当面は消さない）。**
